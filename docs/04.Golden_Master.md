## 1. 목적

단위 테스트(`TVControllerTest`)는 Mockito `verify`로 **개별 행위**를 검증한다. Golden Master는 `TVController` 통합 시나리오를 **결정적 텍스트 트레이스**로 직렬화해, 리팩터링·회귀 시 **튜너 호출 순서·최종 채널**이 한 번에 바뀌지 않았는지 확인한다.

| 구분 | 단위 테스트 | Golden Master |
|------|-------------|---------------|
| 검증 대상 | `setCH` / `seekCH` 호출 여부·인자 | 전체 시나리오 트레이스 문자열 |
| 도구 | Mockito | 파일 비교 또는 ApprovalTests |
| 갱신 | 시나리오별 수정 | baseline 파일 일괄 갱신(의도적 변경 시) |
| CI | `mvn test` 포함 | 동일 (`mvn test`) |

## 2. 아키텍처

```
TVControllerGoldenMasterScenarios.buildMasterTrace()
        │
        ├── RecordingTuner (Fake) ──► setCH / seekCH 기록
        │
        └── TVController.pushButton(...)
                    │
                    ▼
            텍스트 트레이스 (actual)
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
 GoldenMasterSupport      ApprovalTests.verify()
 (classpath .txt)         (*.approved.txt)
```

### 2.1 구성 파일

| 파일 | 역할 |
|------|------|
| `RecordingTuner.java` | 채널 상태 유지 + `setCH` / `seekCH` 호출을 줄 단위 기록 |
| `TVControllerGoldenMasterScenarios.java` | `TVControllerTest` 핵심 17개 시나리오를 하나의 트레이스로 직렬화 |
| `golden/GoldenMasterSupport.java` | 기준 파일 로드·정규화·diff·갱신 |
| `TVControllerGoldenMasterTest.java` | classpath `golden_master_expected.txt`와 비교 (CI 기본) |
| `TVControllerGoldenMasterApprovalsTest.java` | ApprovalTests 승인 파일 비교 (선택) |
| `src/test/resources/golden_master/golden_master_expected.txt` | Git에 보관하는 **기준 출력(baseline)** |

## 3. 트레이스 형식

각 시나리오는 `### 규칙ID: 설명` 헤더와 튜너 호출 로그로 구성된다.

```text
### N-01: 1·확인 → 1번
# initial_ch=0
setCH(1)
# final_ch=1
```

| 줄 접두사 | 의미 |
|-----------|------|
| `### ID: ...` | 시나리오 식별자 (`TVControllerTest` DisplayName과 동일 ID) |
| `# initial_ch=` | 시나리오 시작 채널 |
| `# setup_ch=` | Given 준비(선호 등록·검색 전 채널 설정) |
| `setCH(n)` | `Tuner.setCH` 호출 |
| `seekCH() -> n` | `Tuner.seekCH` 호출 및 반환값 |
| `# final_ch=` | 시나리오 종료 채널 |

## 5. 기준 출력 생성·보관

### 5.1 보관 위치

- **소스**: `src/test/resources/golden_master/golden_master_expected.txt`
- **빌드 후**: `target/test-classes/golden_master/golden_master_expected.txt` (classpath)
- **버전 관리**: baseline은 **반드시 Git에 커밋**한다. CI는 갱신 모드 없이 비교만 수행한다.

### 5.2 최초 생성·의도적 갱신

동작 변경이 **의도된** 경우에만 baseline을 재생성한다.

```bash
# Windows PowerShell
mvn test "-Dtest=TVControllerGoldenMasterTest" "-Dgolden.master.update=true"

# Linux / macOS / CI 로컬
mvn test -Dtest=TVControllerGoldenMasterTest -Dgolden.master.update=true
```

- `-Dgolden.master.update=true` → `GM-01`이 비교를 건너뛰고 `actual`을 repo 경로에 덮어씀.
- 갱신 후 `golden_master_expected.txt` diff를 **코드 리뷰**하고 커밋한다.

### 5.3 갱신 금지 상황

- 테스트 실패를 baseline 덮어쓰기로 “해결”하지 않는다.
- 의도하지 않은 `setCH` / `seekCH` 순서 변경은 **프로덕션 코드 또는 시나리오 정의**를 먼저 수정한다.

## 6. actual vs 기준 파일 비교

### 6.1 실행 흐름 (`TVControllerGoldenMasterTest`)

1. `TVControllerGoldenMasterScenarios.buildMasterTrace()` → `actual`
2. `golden.master.update`가 아니면 classpath에서 `expected` 로드
3. `GoldenMasterSupport.assertMatchesGolden(actual, expected)`
   - CRLF/LF 정규화 후 문자열 전체 비교
   - 불일치 시 **첫 번째 다른 줄 번호**와 expected/actual 한 줄 출력
   - 실패 메시지에 갱신 명령 포함

### 6.2 보조 테스트

| ID | 내용 |
|----|------|
| GM-01 | 마스터 트레이스 ↔ `golden_master_expected.txt` |
| GM-02 | 기준 파일 비어 있지 않음 (CI 누락 방지) |

### 6.3 로컬·CI 실행

```bash
# 전체 테스트 (Golden Master 포함)
mvn test

# Golden Master만
mvn test -Dtest=TVControllerGoldenMasterTest

# 품질 게이트 (JaCoCo 포함)
mvn verify
```

## 7. CI 구성

`.github/workflows/ci.yml`:

- 트리거: `main` / `master` push 및 PR
- JDK 21 (Temurin), Maven cache
- `mvn -B test` — Golden Master는 별도 프로필 없이 Surefire 기본 실행

Golden Master 실패 시 PR은 Red. baseline 갱신은 **로컬에서 update 모드 실행 후 커밋**하는 워크플로만 허용한다.

## 8. (선택) ApprovalTests

### 8.1 개요

`pom.xml`에 `approvaltests` 4.0.2 의존성이 있으며, `TVControllerGoldenMasterApprovalsTest`가 동일 `buildMasterTrace()` 결과를 승인한다.

| 항목 | 내용 |
|------|------|
| 테스트 | `TVControllerGoldenMasterApprovalsTest.masterTraceApproved` |
| 승인 파일 | `TVControllerGoldenMasterApprovalsTest.masterTraceApproved.approved.txt` (테스트 클래스와 동일 패키지) |
| 실패 시 | `.received.txt` 생성 → diff 후 `.approved.txt`로 승인 |

### 8.2 운영 권장

| 방식 | 권장 |
|------|------|
| **리소스 Golden Master** (`golden_master_expected.txt`) | **팀 기준·CI 단일 소스** |
| **ApprovalTests** | IDE 승인 UX 학습·대안; baseline 이중 관리 시 유지보수 부담 |

팀에서 baseline을 하나만 유지하려면 Approvals 테스트를 `@Disabled` 하거나, 리소스 파일만 CI 게이트로 사용한다.

## 9. 단위 테스트와의 역할 분담

| 계층 | 클래스 | 회귀 범위 |
|------|--------|-----------|
| 협력 클래스 단위 | `ChannelInputBufferTest`, `FavoriteChannelsTest`, … | 버퍼·선호·상수 파싱 |
| Controller 단위 | `TVControllerTest` | 규칙 ID별 Mockito 검증 |
| Golden Master | `TVControllerGoldenMasterTest` | 핵심 시나리오 **통합 트레이스** 일괄 회귀 |

리팩터링(`EnumMap` 핸들러 분리 등) 후에도 `mvn test` Green이면 튜너 계약이 유지된 것으로 본다.

## 10. Definition of Done (Golden Master)

- [ ] `golden_master_expected.txt`가 repo에 존재하고 비어 있지 않음
- [ ] `mvn test` 시 `TVControllerGoldenMasterTest` Green
- [ ] 의도적 동작 변경 시 update 모드 → diff 리뷰 → baseline 커밋
- [ ] CI (`mvn -B test`) Green
- [ ] (선택) `TVControllerGoldenMasterApprovalsTest` 승인 파일이 리소스 baseline과 동기화됨
