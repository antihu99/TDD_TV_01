## 1. 현재 구현 스냅샷

```java
public TVController(Tuner tuner) {
    this.tuner = tuner;
    processingCH = "";
}

public void pushButton(remoteKey key) {
    switch (key) {
        case KEY_1:
            processingCH += key.toString();
            break;
        case KEY_OK:
            setTunerCh();
            break;
    }
}

private void setTunerCh() {
    System.out.println("현재 설정하는 채널 : " + processingCH);
    //tuner.setCH(processingCH);
}
```

- 구현된 키: `KEY_1`, `KEY_OK` 만 (`remoteKey`에도 동일 2개만 정의).
- README 요구: 숫자 0~9, 확인, 업/다운, 채널검색, 선호채널, 다음선호채널 등 **다수 키·규칙** → Controller는 **스켈레톤 수준**.

## 2. SOLID 관점

### 2.1 SRP (단일 책임 원칙) 위반·위험

| 지점 | 근거 |
|------|------|
| `pushButton` | 리모컨 **키 라우팅**, **숫자 버퍼 누적**, (향후) **튜너 제어·선호채널·검색 목록**이 한 메서드/클래스에 수렴하는 구조. README §1~6 전부가 이 진입점을 통해 들어옴. |
| `setTunerCh` | **콘솔 출력(표현)** 과 **채널 확정·Tuner 연동(도메인)** 이 한 메서드에 혼재. 프로젝트 규칙상 로그는 테스트 대상이 아님. |
| `TVController` 전체 | `processingCH` 버퍼 관리 + (예정) 선호 목록 + 검색 결과 목록 + 업/다운 정책 → **God Class**로 성장할 전형적 패턴. |

**생성자 `TVController(Tuner tuner)`** 자체는 의존성 주입·초기화만 담당하여 SRP 관점에서 **양호**하다. 위반은 생성자가 아니라 **진화 방향**과 **협력 메서드 책임 혼합**에 있다.

### 2.2 OCP (개방-폐쇄 원칙) 위반·위험

| 지점 | 근거 |
|------|------|
| `switch (key)` | `remoteKey`에 `KEY_2`~`KEY_9`, 업/다운, 검색, 선호 등이 추가될 때마다 **기존 `TVController` 소스 수정** 필요. 확장에 열려 있지 않고 변경에 닫혀 있지 않음. |
| 숫자 키 처리 | `case KEY_1:` 만 존재. 0~9 동일 로직이면 **9개의 case** 또는 반복 수정 → DRY·OCP 동시 위반 예상. |
| 정책 분기 | 일반 업/다운(UD-01~04) vs 검색 목록 업/다운(UD-05~08)은 **조건이 다른 두 정책**인데, switch 한 곳에 넣으면 OCP·복잡도 모두 악화. |

**개선 방향(개념)**: 키별 `KeyHandler` / `Map<remoteKey, Consumer>` / 숫자 키는 `isDigitKey()` 공통 처리로 **신규 키 = 신규 핸들러 클래스** 추가.

## 3. Code Smell 상세

| 스멜 | 해당 여부 | 설명 |
|------|-----------|------|
| **Long Method** | 잠재 (현재는 아님) | `pushButton` 10줄 수준이나, README 전 기능 구현 시 **수십~백 줄 switch** 예상 → Long Method + 높은 순환 복잡도. |
| **Magic Number** | 잠재 | 채널 **0~99**, 2자리 완성, 선호 개수 등 상수 미정의. `""` 초기 버퍼만 있고 `MIN_CHANNEL`/`MAX_CHANNEL` 없음. |
| **Duplicated Code** | 잠재 | `KEY_2`…`KEY_9` 추가 시 `processingCH += key.toString()` **case 복제** 예상. |
| **복잡도** | 낮음 → 급증 예상 | 현재 cyclomatic complexity ≈ 3 (switch 2분기 + 1메서드). 미처리 키는 **묵시적 no-op** (default 없음). |
| **Dead / Commented Code** | 있음 | `//tuner.setCH(processingCH);` — 핵심 협력 호출 비활성화. |
| **Incomplete / Speculative** | 있음 | `tuner` 필드 주입 후 **실사용 없음** (테스트·요구 N-01 미충족). |
| **Inappropriate Intimacy** | 경미 | `remoteKey.toString()`으로 채널 숫자 문자열 생성 — enum이 표현 문자열만 담당하면 허용, 파싱·검증까지 섞이면 경계 모호. |
| **Primitive Obsession** | 있음 | `processingCH`를 `String`으로만 관리 — 0~99 검증, 선행 0(N-07), 2자리 덮어쓰기(N-03) 규칙이 문자열에 산재하기 쉬움. |

### 3.1 요구사항 대비 기능 갭 (품질·설계 영향)

| README / 분석 규칙 | 현재 Controller |
|---------------------|-----------------|
| N-01~N-07 숫자·버퍼·확인 | `KEY_1` + `KEY_OK`만, `setCH` 미호출 |
| UD, S, F, P (업다운·검색·선호) | 미구현 |
| C-01 채널 0~99 | 검증 없음 |
| C-03 Tuner Mock 검증 | `tuner` 미사용 |

## 4. 리팩토링 우선순위 (1~5)

| 순위 | 항목 | 이유 |
|------|------|------|
| **1** | `setTunerCh`에서 **`tuner.setCH` 연동**, `System.out` 제거 | 요구 N-01·OK-01의 **핵심 행위** 미구현. 로그 의존은 테스트 불가·오해 유발. Green 테스트의 전제. |
| **2** | **숫자 키 0~9 공통 처리** + `processingCH` 확정/초기화 규칙 | SRP·Duplicated Code 예방. N-02~N-07 구현의 기반. switch 9벌 복제 방지. |
| **3** | **채널 버퍼(`ChannelInput` 등) 추출** | `TVController`의 God Class화 억제. 2자리 완성·무효화(N-06)를 한 곳에 캡슐화. |
| **4** | **키 처리 OCP 구조** (핸들러/맵) | 업/다운·검색·선호 추가 시 `pushButton` 비대화 방지. |
| **5** | **0~99 상수·검증** 명시 | Magic Number 제거, `Tuner`/`TunerTest`와 IllegalArgumentException 정책 정합. |

> **원칙**: `.cursorrules` — 리팩토링은 **`mvn test` Green 이후**. 현재 `TVControllerTest`는 스켈레톤이므로, 우선순위 1 적용 전 Red→Green 테스트(N-01 등) 추가 권장.

## 6. 생성자 `TVController(Tuner tuner)` 요약

| 항목 | 평가 |
|------|------|
| SRP | **준수** — 의존성 보유·버퍼 초기화만 수행. |
| OCP | **해당 없음** — 생성자는 확장 지점이 아님. |
| Code Smell | **특이 사항 없음** — `tuner` null 검증은 요구 미명시(선택). |
| 권장 | 생성자는 단순 유지; 비즈니스 규칙은 주입된 `Tuner`를 쓰는 **별도 메서드·협력 클래스**로 확장. |
